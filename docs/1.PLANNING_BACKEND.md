# 인스타그램 클론 프로젝트 (High Scalability Platform) 기획서

## 1. 프로젝트 개요
*   **주제**: 대용량 트래픽 처리가 가능한 인스타그램 클론 코어 백엔드 구축
*   **목표**:
    *   수천만 명의 사용자를 가정하여 확장성(Scalability)과 가용성(Availability)이 높은 아키텍처 설계
    *   마이크로서비스 아키텍처(MSA) 도입 및 대용량 데이터 처리 기술 적용
    *   SNS의 핵심 기능(피드, 포스팅, 팔로우)에 대한 최적화된 구현

## 2. 핵심 기능 요구사항 (Functional Requirements)

### A. 사용자 관리 (User Service)
*   회원가입/로그인 (JWT, OAuth 2.0)
*   사용자 프로필 관리 (사진, 소개글 변경)
*   팔로우/언팔로우 기능

### B. 콘텐츠 관리 (Post Service / Media Service)
*   이미지/동영상 업로드 및 최적화 (CDN 연동)
*   게시물 작성, 수정, 삭제
*   해시태그 기능

### C. 소셜 활동 (Activity Service)
*   게시물 좋아요/취소
*   댓글/대댓글 작성
*   실시간 알림 (팔로우, 좋아요, 댓글 등)

### D. 피드 시스템 (Feed Service) - **핵심**
*   **뉴스 피드**: 팔로우한 유저의 게시물을 최신순/알고리즘 순으로 노출
*   **탐색 피드**: 인기 게시물 및 추천 콘텐츠 노출

### E. 검색 (Search Service)
*   사용자 검색
*   해시태그 검색

## 3. 비기능 요구사항 (Non-Functional Requirements)
*   **고가용성**: 단일 장애 지점(SPOF) 제거, 서비스 다중화
*   **확장성**: 트래픽 증가에 따른 수평적 확장(Scale-out) 용이성 확보
*   **성능**: 피드 로딩 속도 200ms 이내 목표 (캐싱 전략 필수)
*   **데이터 일관성**: 최종적 일관성(Eventual Consistency) 모델 채택 (피드 등)
*   **신뢰성**: 메시지 유실 없는 이벤트 처리 및 중복 처리 방지

## 4. 시스템 아키텍처 및 상세 기술 스택 (Technical Stack & Methodologies)

### 4.1. Application Layer (Backend)
*   **Framework**: Spring Boot 3.2.x (Java 21 LTS)
    *   *이유*: Virtual Threads(Project Loom) 지원을 통한 높은 동시성 처리 성능 확보.
*   **ORM / Persistence**:
    *   **JPA (Hibernate 6.x)**: 도메인 객체와 RDBMS 매핑. 복잡한 비즈니스 로직 처리에 활용.
    *   **QueryDSL 5.x**: 타입 세이프한 동적 쿼리 작성 (복잡한 검색 조건 처리).
    *   **Spring Data MongoDB**: 비정형 데이터(댓글, 로그) 처리.
*   **API Interface**:
    *   **RESTful API**: 리소스 중심의 표준 인터페이스 설계.
    *   **Spring Doc (OpenAPI 3.0)**: API 문서 자동화 (Swagger UI).
*   **Security**:
    *   **Spring Security 6**: 인증 및 인가 프레임워크.
    *   **JWT (Json Web Token)**: Stateless 인증 처리.

### 4.2. Development Methodologies (개발 방법론)
*   **DDD (Domain-Driven Design)**: 복잡한 비즈니스 도메인을 해결하기 위한 설계 기법.
    *   **전략적 설계**: Bounded Context를 통한 마이크로서비스 경계 정의 (User Context, Feed Context, etc.).
    *   **전술적 설계**: Aggregate Root, Entity, Value Object, Repository 패턴 적용.
    *   **Layered Architecture**: Controller -> Application Service -> Domain Service -> Infrastructure 계층 분리 철저.
*   **TDD (Test-Driven Development) & Testing Strategy**:
    *   **Unit Test**: JUnit 5, Mockito. 도메인 로직 및 비즈니스 규칙 검증.
    *   **Integration Test**: @SpringBootTest, Testcontainers. DB 및 외부 컴포넌트 연동 테스트.
    *   **Contract Test**: Spring Cloud Contract. 마이크로서비스 간 API 계약 검증.
    *   **Load Test**: nGrinder, k6. 대용량 트래픽 시나리오 검증.
*   **Clean Code & Code Quality**:
    *   **Linting**: SonarLint, Checkstyle.
    *   **Review**: GitHub PR 기반 코드 리뷰 (Convention 준수 확인).

### 4.3. Infrastructure & Middleware
*   **API Gateway**: Spring Cloud Gateway
    *   기능: 라우팅, 로드 밸런싱, JWT 검증, Rate Limiting (Resilience4j).
*   **Database**:
    *   **RDBMS**: MySQL 8.0 (Replication: Source-Replica 구조).
    *   **NoSQL**: MongoDB 6.0 (Sharding Cluster).
*   **Cache & Lock**: Redis 7.0 (Cluster Mode).
    *   라이브러리: Redisson (분산 락 구현).
*   **Message Queue**: Apache Kafka 3.6 (Kraft Mode).
    *   라이브러리: Spring Kafka.
*   **Search**: Elasticsearch 8.x.

## 5. 핵심 기술적 챌린지 및 해결 전략

### A. 피드 생성 전략 (Fan-out)
*   **문제**: 유명인(Celebrity)이 글을 쓸 경우 수백만 명의 팔로워에게 동시에 피드 갱신 필요 (부하 발생)
*   **해결 전략 (Hybrid Approach)**:
    *   **Push Model (Write Fan-out)**: 일반 유저는 글 작성 시 팔로워들의 타임라인 캐시(Redis)에 즉시 ID 삽입 (빠른 읽기)
    *   **Pull Model (Read Fan-out)**: 팔로워가 많은 유명인의 경우, 글 작성 시 별도 처리를 하지 않고, 팔로워가 피드를 조회할 때 해당 유명인의 글을 가져와서 합침 (쓰기 부하 감소)

### B. 데이터베이스 샤딩 (Sharding)
*   **문제**: 단일 DB로는 수십억 건의 게시물 데이터 감당 불가
*   **해결**: User ID 또는 Post ID를 기준으로 DB 샤딩 적용. Application Level Sharding 또는 Spider 같은 솔루션 검토.

### C. 분산 환경에서의 데이터 일관성 (Transactional Outbox Pattern)
*   **문제**: 게시물 저장(DB Transaction)과 피드 발행 이벤트 전송(Kafka)이 원자적으로 수행되지 않으면, DB에는 저장되었으나 이벤트가 발행되지 않는 데이터 불일치 발생 가능.
*   **해결 전략**:
    1.  **Outbox Table**: 비즈니스 로직 수행 시, 동일 트랜잭션 내에 이벤트를 `Outbox` 테이블에 저장.
    2.  **CDC (Change Data Capture)**: Debezium 등의 도구를 사용하거나 별도의 Polling Publisher가 `Outbox` 테이블을 감지하여 Kafka로 메시지 발행.
    3.  **Result**: 'At-least-once' 전달 보장.

### D. 동시성 제어 (Concurrency Control)
*   **문제**: 인기 게시물에 '좋아요' 요청이 동시에 수만 건 몰릴 경우 카운트 유실(Race Condition) 발생. 재고 차감과 같은 상황.
*   **해결 전략**:
    *   **Redis Distributed Lock (Redisson)**: 락을 획득한 요청만 처리. (강력하지만 성능 저하 우려)
    *   **Optimistic Locking**: JPA `@Version` 활용. 충돌 시 재시도.
    *   **Redis HyperLogLog**: 정확한 숫자가 아닌 '대략적인' 카운트가 허용될 경우 메모리 효율적인 자료구조 사용.
    *   **Write-Behind (Eventual Consistency)**: 좋아요 요청을 즉시 DB에 쓰지 않고 Redis에 버퍼링했다가 배치로 DB 업데이트.

### E. 멱등성 보장 (Idempotency)
*   **문제**: 네트워크 타임아웃 등으로 인해 클라이언트가 동일한 요청(게시물 생성, 결제 등)을 중복 전송하거나, Kafka 컨슈머가 메시지를 중복 수신.
*   **해결 전략**:
    *   **Idempotency Key**: API 요청 헤더에 고유 키 포함. 서버는 키를 Redis에 저장하여 중복 요청 필터링.
    *   **Consumer Check**: 메시지 처리 전 처리된 Message ID인지 확인.

### F. 장애 격리 (Circuit Breaker)
*   **문제**: 미디어 변환 서비스 장애 시 전체 글쓰기 기능 마비.
*   **해결 전략**: Resilience4j 등을 활용하여 특정 서비스 응답 지연/오류 시 빠른 실패(Fast Fail) 처리 및 대체 로직(Fallback) 수행.

## 6. 개발 단계 (Milestones)

1.  **Phase 1 (MVP)**: 모놀리식으로 시작 혹은 핵심 서비스(User, Post)만 분리하여 기본 기능 구현. RDBMS 위주 설계.
2.  **Phase 2 (Optimization)**: Redis 캐싱 도입, 피드 시스템(Push Model) 구현.
3.  **Phase 3 (Reliability)**: **Outbox Pattern** 적용, **동시성 테스트**(jMeter/nGrinder) 및 락 적용, Circuit Breaker 도입.
4.  **Phase 4 (Scale-out)**: 서비스 완전 분리(MSA), Kafka 도입(비동기 처리), DB 샤딩 및 부하 분산 테스트.
