# 데이터 스키마 및 모델링 설계 (Schema Design)

## 1. 개요 및 전략
*   **Polyglot Persistence**: 데이터의 특성에 따라 RDBMS(관계형)와 NoSQL을 혼용합니다.
*   **Sharding (Database Partitioning)**: `Users`와 `Posts` 테이블은 데이터 양이 급증하므로 **User ID**를 기반으로 수평 분할(Sharding)을 고려하여 설계합니다.
*   **Denormalization (비정규화)**: 읽기 성능(Read Performance)을 극대화하기 위해 Feed 시스템 등에서는 중복 데이터를 허용합니다.

---

## 2. RDBMS (MySQL / MariaDB)
핵심 비즈니스 데이터(사용자, 게시물 원본, 관계)를 저장합니다.

### 2.1. Users (사용자)
*   **Sharding Key**: `user_id`
*   **Note**: 인증 및 프로필 정보.

| Column Name | Type | Key | Description |
| :--- | :--- | :--- | :--- |
| `id` | BIGINT | PK | 사용자 고유 ID (Snowflake ID 등 사용 권장) |
| `email` | VARCHAR(255) | UQ | 로그인 이메일 |
| `username` | VARCHAR(30) | UQ | 사용자 핸들 (@nickname) |
| `password` | VARCHAR(255) | | BCrypt 암호화된 비밀번호 |
| `name` | VARCHAR(50) | | 표시 이름 |
| `bio` | VARCHAR(150) | | 자기소개 |
| `profile_img` | VARCHAR(255) | | 프로필 이미지 URL |
| `created_at` | DATETIME | | 가입일 |

### 2.2. Posts (게시물)
*   **Sharding Key**: `user_id` (특정 유저의 피드를 빠르게 가져오기 위함)

| Column Name | Type | Key | Description |
| :--- | :--- | :--- | :--- |
| `id` | BIGINT | PK | 게시물 고유 ID |
| `user_id` | BIGINT | FK, IDX | 작성자 ID |
| `image_url` | TEXT | | 미디어 URL (JSON Array로 다중 이미지 처리 가능) |
| `caption` | TEXT | | 게시물 본문 |
| `created_at` | DATETIME | IDX | 작성 시간 (Range Query용) |
| `updated_at` | DATETIME | | 수정 시간 |

### 2.3. Follows (팔로우 관계)
*   **Sharding Key**: `follower_id` (내가 팔로우한 사람 목록 조회가 빈번함)

| Column Name | Type | Key | Description |
| :--- | :--- | :--- | :--- |
| `follower_id` | BIGINT | PK(Composite) | 팔로우 **하는** 사람 (Subject) |
| `followee_id` | BIGINT | PK(Composite) | 팔로우 **받는** 사람 (Target) |
| `created_at` | DATETIME | | 팔로우 시점 |

## 3. NoSQL (MongoDB / DynamoDB)
쓰기 부하가 심하거나 스키마 유연성이 필요한 데이터입니다.

### 3.1. Post_Likes (좋아요) - *High Write Throughput*
RDBMS에 저장할 수도 있지만, 대용량 트래픽 시 NoSQL이나 Redis 버퍼링 후 저장이 유리합니다.

*   **Structure**:
    ```json
    {
      "_id": "post_1001_user_505",
      "post_id": 1001,
      "user_id": 505,
      "created_at": "2024-12-18T10:00:00Z"
    }
    ```
*   **Indexes**: `post_id` (Count 집계용), `user_id` (내가 좋아한 글 조회용)

### 3.2. Comments (댓글)
계층형 구조(대댓글) 표현 및 샤딩 용이성을 위해 NoSQL 고려 가능.

*   **Structure**:
    ```json
    {
      "_id": "comment_999",
      "post_id": 1001,
      "user_id": 505,
      "content": "좋은 사진이네요!",
      "parent_id": null, // 대댓글일 경우 상위 댓글 ID
      "created_at": "..."
    }
    ```

### 3.3. Feed_Delivery (뉴스 피드 - Pull/Push Hybrid)
사용자별로 미리 생성된 피드 목록(Materialized View). **가장 중요한 부분**.

*   **Collection**: `timelines`
*   **Key**: `owner_id` (피드 주인)
*   **Structure**:
    ```json
    {
      "owner_id": 123,
      "posts": [
        {
          "post_id": 98765,
          "author_id": 456,
          "created_at": "2024-12-18T12:00:00Z" 
          // 필요한 경우 썸네일 URL 등 일부 데이터 중복 저장 (Denormalization)
        },
        ...
      ]
    }
    ```

## 4. Redis (Cache & In-Memory)
초고속 접근이 필요한 데이터 및 임시 저장소.

### 4.1. Caching
*   **User Profile**: `user:profile:{userId}` (TTL: 30min) -> RDBMS 부하 감소
*   **Hot Post**: `post:detail:{postId}` (TTL: 10min) -> 인기 게시물 캐싱

### 4.2. Feeds (Active User Timeline)
*   **Data Structure**: Sorted Set (ZSET)
*   **Key**: `timeline:{userId}`
*   **Score**: `timestamp` (최신순 정렬)
*   **Value**: `postId`
*   **설명**: 최근 활동한 유저들의 피드 ID 목록을 Redis에 유지하여 RDBMS/NoSQL 조회 없이 즉시 피드 노출. (예: 최신 100개만 유지)

### 4.3. Counters (Write-Behind Buffer)
*   **Key**: `post:like_count:{postId}`
*   **Logic**: 좋아요 발생 시 Redis `INCR` -> 일정 주기로 RDBMS/NoSQL에 Flush.

## 5. 데이터 흐름 예시 (Data Flow)

### 게시물 작성 시 (Write Path)
1.  **Posts** 테이블(MySQL)에 데이터 Insert.
2.  (비동기) 팔로워 조회 -> **Redis Timeline** (`timeline:{followerId}`)에 Post ID 추가 (Fan-out).
3.  (비동기) 검색 엔진(Elasticsearch)에 해시태그 인덱싱.

### 피드 조회 시 (Read Path)
1.  **Redis Timeline** 조회 (`ZREVRANGE timeline:{myId} 0 19`).
2.  Post ID 목록 획득.
3.  Post 상세 정보(이미지, 내용)는 **Redis Cache**(`post:detail:{id}`)에서 조회 (없으면 DB 조회 후 캐싱).
4.  클라이언트에 반환.
